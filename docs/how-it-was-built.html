QuickCanteen

How the food-ordering website and Android app were built

Built 23 to 30 September 2026  ·  27 commits  ·  285 automated tests

1. What it is

QuickCanteen lets customers order food from their phone, confirm the order with a 4-digit code sent to their email, watch the order move from Placed to Preparing to Ready in real time, and collect it at the counter with a token number. The kitchen sees every order the moment it is placed. The owner gets an admin panel with live orders, earnings, the menu, stock, bills and users. When an order is collected, a bill is saved and emailed to the customer.

It has three kinds of user, each with its own screens:

RoleSigns in withWhat they can do
CustomerTheir own email, registered on the siteBrowse the menu, add to cart, confirm with a code, track the order, see past orders and bills, order again
Kitchenkitchen@canteen.citSee incoming orders, tap Start, Ready and Collect, reject an order, manage stock, open or close the canteen
Adminadmin@canteen.citEverything the kitchen can do, plus the dashboard, all orders with earnings, menu editing, bills, users and settings

4. How an order works, step by step

Add to cart→Place order→Code by email→Placed→Preparing→Ready→Collected + bill
  1. Cart. The cart is kept on the customer's phone. Nothing is reserved until the order is placed.
  2. Code. Tapping Place order sends a random 4-digit code to the customer's email. The code lasts 5 minutes, allows 5 wrong tries, and can be re-sent after 30 seconds. This stops prank orders.
  3. Placing. Once the code is correct, the server does everything in one database transaction: it checks the canteen is open, checks each dish is available, takes stock, gives the next token number for the day (starting at 101), and saves the order. If anything fails, nothing is saved.
  4. Kitchen. The order appears instantly on the kitchen board. Staff tap Start, then Ready. The customer's phone updates each time and plays a chime at Ready.
  5. Collection. Staff type the token number and tap Collect. In the same transaction a bill is created as a permanent copy of the order (name, mobile, dishes, prices, total, times). The bill is then emailed to the customer.
Why the order is safe against mistakes. Stock can never go below zero even if ten people order the last three items at the same moment: exactly three succeed. A double tap on Place order creates one order, not two. Two staff tapping the same order at once cannot both succeed; the second is told it was already updated.

6. What is stored in the database

TableWhat it holds
UserName, email, mobile number, hashed password and role. One account per email and per mobile number.
Category, MenuItemThe menu: name, price, photo, veg or non-veg, stock, prep time, spice level, calories, ingredients, allergens, badges and pairings. Removed dishes are archived, not deleted, so old orders still show them.
Order, OrderItemEach order with its token, status, total and times; each line copies the dish name and price at the moment of ordering, so later price changes do not alter past orders.
DailyCounterThe last token number given out each day.
OtpChallengeOrder codes, stored only as a keyed hash, with expiry and attempt count.
Bill, BillLineThe permanent bill made at collection, and when it was emailed.
SettingsName, open or closed, closed message, minutes per order, opening hours and location.

Money is stored in paise (₹50 is saved as 5000) to avoid rounding errors. Times are stored in UTC and shown in Indian time.

7. Security and abuse protection

  • Passwords are hashed with bcrypt. Order codes and tokens are stored only as keyed hashes, so a database leak does not reveal usable codes.
  • The session cookie cannot be read by page scripts (httpOnly) and every server endpoint checks the user's role itself.
  • Limits: 5 codes an hour per mobile number, 60 an hour per network address, and a 30-second wait between codes. Login and registration are rate-limited too.
  • Kitchen staff see a customer's first name and a masked phone number only. The full number is visible to the customer and the admin.
  • Passwords and keys are never in the code. They are kept as hidden settings on Vercel and as private secrets on GitHub.

8. How live updates work

Each open page keeps a WebSocket connection to the server and is placed in "rooms": everyone is in public, each customer is in a private room, staff are in kitchen, admins in admin. When something changes, the server sends an event only to the rooms that should see it, and only after the database has saved the change.

On Vercel, requests are handled by many short-lived server instances, and a connection is tied to one of them. So every event is first published to Redis, and every instance forwards it to its own connected phones. If a phone loses its connection, it reconnects by itself (waiting 1 to 30 seconds) and reloads the latest data, so nothing is missed.

9. The design journey

The look went through three versions, guided by feedback:

  1. First version: a warm "banana leaf and turmeric" theme with a heavy display font and interactive 3D models of each dish built in Three.js.
  2. Simplified: the 3D views and heavy styling were removed when the request became "simple, no more 3D".
  3. Final: rebuilt in the style of Domino's and Thalappakatti-type ordering sites: a red brand bar, a light page, one typeface, category buttons with photos that follow the scroll, dish rows with a photo and an ADD button that becomes a − 1 + counter, and a cart bar at the bottom. On larger screens the rows become a grid of cards.

The menu was replaced at the same time: pizzas, burgers, sides, wraps and sandwiches, coffee and drinks, and desserts. All 30 photos are freely licensed images from Wikimedia Commons, chosen by eye to avoid brand logos, cropped to one shape, and credited on the site's Credits page as their licences require.

10. Putting it online

  • The code is on GitHub. Every push to the main branch makes Vercel build and publish a new version automatically, usually in about two minutes.
  • During each build the database is brought up to date: structure changes are applied, and the starter data (staff accounts and the menu) is created if missing. Existing data and any changes made in the admin panel are never overwritten.
  • The database (Neon) and Redis (Upstash) were added from Vercel's marketplace on their free plans, in the same Singapore region as the server to keep it fast.
  • Email uses a Gmail account with an app password, a separate 16-letter password made only for this app. It is saved on Vercel as a hidden setting.

11. The Android app

There are two ways to have it as an app, and both show the same live site:

  • Install from the browser. The site describes itself as an app (name, icon, colours), so Chrome offers "Install app" and iPhone's Safari offers "Add to Home Screen".
  • Android APK. A small Capacitor project in the mobile/ folder wraps the site. This PC did not have enough free memory to build it, so GitHub builds it in the cloud, signs it with a private key, and publishes it as a download. Rebuilds happen automatically when the mobile/ folder changes.
The signing key matters. It is kept in C:\Users\sreev\Projects\campus-canteen-keys\ and as private GitHub secrets. Every future update of the app must be signed with the same key, so keep a private backup and never share it.

Because the app opens the live site, website updates appear in the app straight away with nothing to reinstall. It needs an internet connection.

13. Problems met and how they were solved

ProblemWhat fixed it
Live updates did not work on VercelThe first version used Socket.IO on one long-running server. Vercel has no such server, so it was rewritten with plain WebSockets and Redis passing events between instances.
Order codes never arrivedThe site was in test mode, printing codes to the log. Free SMS needed a phone kept online, and free email services need an owned domain. Gmail's own mail server solved both.
Gmail rejected the first passwordThe app password was not accepted for the account. A new one was created and tested before being saved.
Editing one field of a dish reset its stockA quirk in the input-checking library re-applied default values on partial updates. The update rule was rebuilt without defaults, with a test to keep it fixed.
Pages wider than the phone screenFound twice. First, hidden accessibility labels inside a side-scrolling row escaped its edges. Later, three admin pages stretched to their widest row. Both were fixed at the cause, and a test now checks every page.
The PC ran out of memoryBuilds and browser tests crashed when memory was full. Heavy work (the Android build) was moved to GitHub's servers.
Wrong photos from searchAutomatic image search returned packaging, logos and the wrong dishes. Each photo was reviewed by eye and replaced where needed.
