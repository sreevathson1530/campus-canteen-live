At a glance

One canteen, one live source of truth.

Students order from their phones and get a daily token number. The kitchen sees the order the moment it's placed and moves it along with one tap. Every change reaches every phone within a second, with no refresh.

Order ahead

Browse a 3D menu, build a cart and confirm with a 4-digit code sent to your phone. You get a token like 107.

Watch it live

Your tracker shows your place in the queue, an estimated wait, and each step: Placed → Preparing → Ready.

Pick up

When it's ready your phone chimes and vibrates. Show the token, pay by cash or UPI at the counter, and you're done.

02 · The student journey

A student's order, start to finish.

Here's what happens between opening the app and walking away with food. Each step shows what the student sees and what the system does.

  1. Register once. Name, email, password, optional roll number and a 10-digit mobile number (+91). Each number can belong to one account only, which stops people making several accounts to send fake orders.
  2. Open the menu. Dishes are grouped under sticky category tabs (Breakfast, Meals, Snacks, Beverages). Each card shows a 3D-rendered still of the dish, its price in ₹, a veg/non-veg marker, and "Only N left" or "Sold out" when relevant. All of it updates live.
  3. Look closer (optional). Tap a dish and a sheet slides up with a live 3D model: drag to spin, pinch to zoom, with steam rising from hot items.
  4. Build the cart. Up to 10 of any one item and 10 different items. The cart is saved on the phone, so it survives a refresh. Add a note like "less spicy".
  5. Place order → verify. A 4-digit code is sent by SMS to the student's registered number. They type it in (or the phone fills it in automatically). No correct code, no order.
  6. Get a token. The order is placed in a single database transaction. The student gets token 107 and lands on the live tracker. At the same moment the order appears on every kitchen phone with a tone.
  7. Wait, informed. "You are #3 in the queue · about 9 min" updates live as orders ahead move. The stepper goes Placed → Preparing.
  8. Ready. The screen turns green: "Ready, show token 107 at the counter", with a chime, a vibration, and a browser notification if the tab is in the background.
  9. Collect and pay. Staff type 107 into the Collect box. The student pays by cash or UPI at the counter, and the order becomes Collected. The bill is created at that moment and appears on the student's phone.

If something goes wrong: if the kitchen rejects an order, the student sees the reason ("Item ran out") and "You have not been charged", and any limited stock goes back on sale. If the canteen closes, every menu shows a banner and ordering is disabled, while orders already in progress carry on.

What each screen is built for

  • Menu: built to load fast. The 3D stills are small images, so the grid is usable within 2 s on 4G.
  • Dish viewer: 3D only loads when you ask for it. Without WebGL, or with reduced motion on, it shows the still instead.

  • Ready: fills the whole screen so it can't be missed. Colour is never the only signal; there's always text too.
04 · Phone verification

No code, no order.

So that nobody can place orders for fun, every order needs a fresh 4-digit code sent to the student's registered mobile number. The server enforces this, not just the app.

The code proves the student has the phone. The single-use token ties that proof to exactly one order.

The rules

RuleValue
Code length4 digits, random
Code lifetime5 minutes
Wrong tries allowed5, then the code is locked
Resend cooldown30 seconds
Send limit5 per hour per number · 10 per hour per IP
Verified tokenSingle use · valid 10 minutes · this user only
StorageOnly hashes of the code and token are stored
Numbers+91, 10 digits, one account per number

Edge cases

  • Double-tap or network retry: the PRD's Idempotency-Key is checked before the token, so a retry gets back the same order instead of a "code already used" error.
  • Order fails after verifying (e.g. out of stock): the token is only used up if the order transaction commits, so the student can fix the cart and try again without a new code.
  • SMS late at rush hour: the resend button unlocks after 30 s, and the timer shows how long the code is valid.
  • Gateway phone offline: the send fails with a clear message ("Couldn't send the code, try again or ask the counter") and staff get an alert.

Sending SMS for free: your own Android phone

An old Android phone with a SIM runs a free, open-source gateway app (textbee or SMS Gateway for Android). The server calls the app's API, and the phone sends the SMS from its own SIM. There are no per-message fees and no DLT registration.

Good for

  • College projects and a single canteen
  • Zero cost on a normal prepaid plan
  • Setup takes minutes

Limits to know

  • Most Indian prepaid plans include ~100 free SMS a day, so with a code per order that's about 100 orders a day
  • The phone must stay on and online
  • Codes come from a personal number

Built to be swapped. The SMS sender sits behind a small interface (src/lib/sms/) with three versions: console (prints the code in the terminal during development), android-gateway, and a paid provider (MSG91 / Twilio) added later in a single file. In development and tests a fixed OTP_DEV_CODE lets the simulator and tests get through; the server refuses to start in production if it's set.

05 · The order lifecycle

Six statuses. Only these moves are allowed.

The server rejects any other move with INVALID_TRANSITION. Collected, Cancelled and Rejected are final.

From → ToWhoWhat else happens
Placed → PreparingStaff, AdminSets preparingAt. The tracker and queue positions update live.
Placed → CancelledThe student who owns itLimited stock is restored. The order leaves the kitchen board.
Placed or Preparing → RejectedStaff, Admin (reason 3–140 chars)Stock restored. The student sees the reason and "You have not been charged".
Preparing → ReadyStaff, AdminSets readyAt. The student's phone chimes, vibrates and notifies.
Ready → CollectedStaff, AdminSets collectedAt. Means it was paid for and handed over. Creates the bill in the same transaction.

Queue position and wait

The queue is today's Placed and Preparing orders, oldest first. Position = place in that list; estimated wait = position × minutes per order (default 3, set by the admin). Every time the queue changes, each waiting student gets their new position, live.

How it behaves

  • New orders flash for 3 seconds and play a tone. The tab title shows "(2) New · Kitchen". Sound starts only after a tap on "Enable sound", because browsers block autoplay.
  • One big button per card: Start → Ready → Collected. Reject is under the ⋯ menu, with quick reasons ("Item ran out", "Kitchen closing") or a custom one.
  • Timers tick every second: neutral under 10 min, amber from 10 to 20, red after 20. Ready cards older than 15 minutes get an "Uncollected" badge.
  • Optimistic: the card moves the instant you tap. If another staff member got there first, it moves back and a toast says "Already updated by another staff member".
  • Collect box: type 107 and press Enter to mark that Ready order Collected. It shows an error if 107 isn't Ready.
  • Swipe between the New, Preparing and Ready tabs. The count on each tab updates live, so staff can see work waiting in other tabs.
  • Done today drawer: the last 20 finished orders.
  • If the connection drops for more than 3 s, a banner says "Reconnecting, board may be out of date".

Privacy: the kitchen sees only a student's first name, never their email, roll number or phone.

07 · Stock, status and admin

Running the canteen from a phone.

Stock and status · /kitchen/stock

  • Canteen Open / Closed switch with an optional message ("Back at 2 PM"). When closed, every menu shows the banner and ordering is disabled.
  • Every item has an availability switch and a stock number (blank means unlimited).
  • Changes save automatically after 500 ms and reach every open menu live.
  • Items with 5 or fewer left are highlighted.

Live dashboard · /admin

  • Stat cards: orders today, revenue today (collected orders), active orders, average prep time, cancelled plus rejected.
  • Orders per hour (bar chart) and top 5 items today.
  • Who's online: kitchen phones and students.
  • Updates at most once per second.

Menu management · /admin/menu

  • Create, edit and reorder categories and items (name, description, price, veg, prep minutes, stock, availability).
  • Each item is linked to its 3D model and still image.
  • Deleting archives an item: hidden from the menu, kept for order history.

Users and settings · /admin/users, /admin/settings

  • Search users by name, email, roll number or phone. Create staff accounts and change roles.
  • Settings: canteen name, minutes per order, max active orders per student, open/closed.
  • New: the SMS gateway's status (online or offline, codes sent today against the daily limit).

Mobile-first layout rules

  • Everything is designed from 360 px wide upwards. On larger screens it gets more room, not a different app.
  • Main actions sit in the bottom third of the screen, within thumb reach. Tap targets are at least 44 px.
  • Tables on admin pages become stacked cards on a phone. The chart scrolls sideways inside its own box.
  • Dark mode follows the system setting. Every page has a Live / Reconnecting / Offline badge in the header.
08 · How "live" works

Commands go in over HTTP. Events come out over WebSocket.

Every change (placing an order, tapping Ready, switching an item off) is an HTTP request the server checks and saves in a transaction. Only after it's saved does the server push an event to the right people over Socket.IO. Phones never write through the socket.

Rooms: who hears what

RoomMembers
publicEvery connection: menu and open/closed
user:{id}All tabs of one student: their orders and queue position
kitchenStaff and admin: new and updated orders
adminAdmins: live stats and presence

The server puts each connection in its rooms based on the login cookie. Clients can't choose. The PRD's display room is removed along with the TV.

Events

EventSent when
order:createdAn order is placed
order:updatedAny status change
queue:updateThe queue gains or loses an order
menu:item-updatedStock, availability, price or name changes
menu:changedItems or categories added, archived or reordered
canteen:statusOpen/closed or settings change
stats:updateAny order change, at most once a second
presence:updateSomeone connects or disconnects

Snapshot + events. Each screen first loads a snapshot over HTTP, then applies events on top of it. Whenever the connection comes back (after a dropped signal or a server restart), the screen reloads its snapshot, so anything missed while offline shows up. No screen ever polls on a timer.

09 · Staying correct

Correct at the lunch rush, not only in the demo.

The hard part isn't the happy path. It's two people tapping at the same moment, and phones losing signal in a crowded canteen.

What happensHow the app stays correct
Two students order the last Samosa at the same momentStock is reduced with a conditional update ("only if stock ≥ quantity") inside the order transaction. Exactly one order succeeds; the other gets OUT_OF_STOCK. Stock never goes below 0.
Two staff tap Ready on the same cardEvery order has a version number. The second tap carries an out-of-date version, gets VERSION_CONFLICT, and its card moves back to the server's state.
Student double-taps Place order, or the network retriesAn Idempotency-Key is created when the cart opens, and the database allows each key only once. The retry returns the same order.
The same OTP token is used for two ordersUsing up the token is also a conditional update inside the order transaction. Only one order can use it; the other gets OTP_REQUIRED.
Two orders need a token number at onceA daily counter is incremented inside the transaction, and the database won't accept a duplicate (date, token). Tokens restart at 101 each day.
Events arrive out of orderThe phone ignores any order event whose version isn't newer than what it already has.
A price is changed in the app codeIgnored. Totals are always calculated from database prices.
Many writes hit SQLite at onceWAL mode and a 5-second busy timeout are set at startup.

When the connection drops

Reconnecting

The header badge turns amber. Socket.IO retries automatically with backoff.

Back online

Every screen reloads its snapshot, so changes made while it was offline appear without a manual refresh.

Server restart

All phones reconnect and resync by themselves. On shutdown the server closes sockets and the database cleanly.

Performance targets

  • 95% of events reach phones within 1 second on the local network.
  • 200 connected phones on a normal laptop.
  • The student menu is usable within 2 seconds on a mid-range phone over 4G. The 3D stills are small images, and the Three.js viewer only loads when a dish is opened.
10 · Security and privacy

Trust the server, never the phone.

  • Sessions: a signed JWT in an httpOnly, SameSite=Lax cookie, valid 7 days (Secure in production). The server won't start without a strong secret.
  • Passwords are hashed with bcrypt. Login errors never reveal whether an email exists.
  • Role checks happen in every route handler and server layout, never only in the UI.
  • Server-side checks: prices, roles, stock, status and OTP are all checked again on the server.
  • Write requests accept only JSON, which blocks cross-site form posts.
  • Rate limits: 5 orders a minute per user, 10 logins a minute per IP, plus the OTP send limits (section 04). Too many requests get RATE_LIMITED.
  • OTP: codes and tokens are stored only as hashes. Codes are never logged in production.
  • Privacy: the kitchen sees first names only. Only admins see email, roll number and phone. Phone numbers are masked on screen (••••• •4821).
  • Redirects: the ?next= redirect accepts only relative paths.
  • Error responses never include stack traces.

Accessibility

  • WCAG 2.1 AA contrast, visible focus rings, and a kitchen board that works with a keyboard.
  • Status is never shown by colour alone; every state has text or an icon. Changes are announced with an aria-live region.
  • Reduced motion turns off pulses, slide animations and 3D auto-rotation, and shows 3D stills instead of live models.
  • The OTP inputs work as one field for screen readers and support the phone's automatic code fill.
11 · Design direction proposal

Banana leaf, turmeric, chili.

The look draws on a real South Indian college canteen: banana-leaf green, turmeric yellow, chili red and a warm off-white like a paper menu. The food is the hero: every dish is shown on its own, with no plates or props. The aim is a friendly, appetising app that feels local, not a generic food-delivery template.

3D food: the hybrid approach (agreed)

1 · One model per dish

Each of the 16 dishes gets a 3D model of the food alone, with no plate, floating over a soft shadow with matching lighting. Drinks keep their cup.

2 · Stills for the menu

A render script photographs each model once into a small WebP (~30 KB). The menu grid uses these, so it stays fast on 4G.

3 · Live viewer on tap

Tapping a dish loads the Three.js viewer (react-three-fiber + drei): drag to spin, pinch to zoom, steam on hot items, soft shadow.

Still to decide: the style of the models. (a) Stylised, built in code: clay or toy-like, tiny files, perfectly consistent, fully controllable. (b) Realistic, AI-generated from food photos (e.g. image-to-3D models): closer to real food, textured, ~1–3 MB each, and the quality varies so they need cleanup. Side-by-side previews will be shown before choosing.

12 · Data and API (continued)

Where the order records are stored.

Every order is stored in one place: a database file on the computer or server running the app. Phones only show copies. If a phone is lost or the app is closed, no order data is lost.

Phones send requests. Only the server writes to the database file.

What's recorded for each order

TableWhat it holds
OrderToken number, business date, status, total (in paise), note, reject reason, which student, and the time of every step: placed, preparing, ready, collected, closed.
OrderItemEach line of the order: item, quantity, and a copy of the name and price at the time of ordering, so later menu edits never change old orders.
DailyCounterThe last token number used each day (starts at 101).
Bill, BillLineThe bill of every collected order: bill number, student name and mobile, dishes with rate and amount, total, and the times. Never edited.
OtpChallengeEach verification: the phone number, a hash of the code (never the code itself), tries, and which order it was used for.
User, MenuItem, SettingsAccounts, the menu and stock, and canteen settings.

How long it's kept

  • Forever. Nothing is deleted automatically.
  • Cancelled and rejected orders are kept, with their reason.
  • Students see 30 days in My orders; older orders stay in the database.

What stays on phones

  • Only the cart, until the order is placed.
  • A temporary copy of the screen that disappears when the app closes.
  • The gateway phone keeps the sent code SMS.

Keep the file safe

  • Back up by copying dev.db while the app is stopped.
  • npm run db:reset wipes all orders.
  • Free cloud hosts wipe the disk on redeploy, so use a persistent disk or switch to PostgreSQL (a one-line change).

Hosting: needs a server that keeps a Node process running, such as Render, Railway, a VPS or your laptop on the campus Wi-Fi. Vercel can't hold WebSocket connections open, so it isn't a target. For the demo, phones on the same Wi-Fi open http://<laptop-IP>:3000.

Project location: keep the code outside OneDrive (e.g. C:\Users\sreev\projects\campus-canteen-live). OneDrive tries to sync node_modules and the SQLite file, which is slow and can lock files.
