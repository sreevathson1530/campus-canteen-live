 1. Overview and goals

  Campus Canteen Live lets students order canteen food from their phones and watch
  each order move from kitchen to counter in real time. Every screen (student phone,
  kitchen tablet, counter TV, admin dashboard) shows the same server state within one
  second, with no page refresh.
  Problem. At break time, students crowd the counter and wait without knowing when their
  food will be ready. Staff have no live view of the queue, and students only find out an item
  is sold out when they reach the counter.
  Solution. Students order ahead and get a daily token number. The kitchen sees orders
  arrive instantly and advances each one with a single tap, while a counter TV shows which
  tokens are being prepared and which are ready. Stock levels, sold-out items and
  open/closed status update live for everyone.

 Goals

      A new order appears on the kitchen board within 1 second of being placed (on a local
      network).
      Every status change reaches the student's phone and the counter display within 1
      second, with no refresh.
      Limited-stock items are never oversold, even when two students order the last unit at
      the same moment.
      Clients recover by themselves after a dropped connection and end up showing the
      correct state.
      A fresh clone runs locally with one setup command and one dev command, on
      Windows, macOS and Linux.

 Learning objectives

      WebSockets with Socket.IO: rooms, broadcast versus targeted events, and
      authenticated connections.

Glossary

    Token: a daily order number (101, 102, ...) that the student shows at pickup.
    Business date: the calendar date in the canteen's timezone. Tokens restart at 101 on
    each business date.
    Queue: today's orders in PLACED or PREPARING status, oldest first.
    Active order: an order in PLACED, PREPARING or READY status.
    Paise: all money is stored as whole-number paise (1 = 100 paise) and displayed in
    rupees.

 Core flows

   1. Order ahead. A student opens /menu, adds items to the cart, adds an optional note
      ("less spicy") and places the order. They land on /orders/[id], which shows token 107,
      their queue position and an estimated wait.

   2. Kitchen processing. The new card appears in the kitchen's New column with a tone.
      Staff tap Start (the card moves to Preparing), then Ready (the card moves to Ready).
      The student's phone and the counter TV update each time.

   3. Pickup. The student sees "Ready, show token 107" with a chime and vibration. At the
      counter, staff type 107 into the Collect box (or tap the card) and the order becomes
      COLLECTED. It then disappears from the TV.

   4. Sold out mid-rush. Staff switch off Masala Dosa, or its stock reaches 0. Every open
      menu greys it out instantly. Carts that contain it show a warning, and the server
      refuses any order that includes it.

   5. Rejection. Staff reject an order with a reason ("Item ran out"). The student sees the
      reason immediately, and any limited stock is returned.

   6. Canteen closes. Staff flip the canteen to Closed with a message ("Back at 2 PM"). All
      menus show a banner and disable ordering, and the TV shows a closed screen. Orders
      already in progress continue normally.

5.2 Socket connection and authentication

    Socket.IO is attached to the same HTTP server and port as Next.js, at path /socket.io.
    The browser sends the session cookie automatically, because the socket is on the
    same origin. Server middleware verifies the JWT and sets socket.data.user = { id,
    role, firstName } .
    The counter TV connects with auth: { client: "display" } and no login. It joins
    only the public and display rooms.
    Any other connection without a valid session is rejected with the error
    UNAUTHORIZED.
    After connecting, the server joins each socket to rooms based on its role.

5.5 Client rules

1. Each browser tab opens one socket inside a SocketProvider, and the socket
    disconnects on logout.

2. Every page loads a snapshot over REST with TanStack Query, then applies socket
    events on top of it.

3. On every connect event, both the first connection and every reconnect, the client
    invalidates its queries and refetches the snapshot. This makes it correct after missed
    events.

4. Events patch the TanStack Query cache with setQueryData . Components never keep
    a separate copy of server data.

5. Apply order:updated only if the payload's version is greater than the cached version.
    Stale or out-of-order events are dropped.

6. display:update replaces the display's state completely, so applying it twice is
    harmless.

5.6 Emitting from route handlers

    server.ts creates the Socket.IO instance and stores it on globalThis.__io . getIO()
    in src/lib/realtime/io.ts reads it from there. This is required because Next.js can load
    route handlers in separate module instances, so a normal module-level singleton would
    be undefined inside them.

   All emits go through functions in src/lib/realtime/emitters.ts: emitOrderCreated,

6.1 Placing an order (src/lib/orders/service.ts: placeOrder)

1. If an order with the same idempotencyKey already exists for this user, return it with
    HTTP 200 and create nothing new.

2. Validate the body with Zod: 1-10 lines, each with a quantity from 1 to 10, and a note of
    up to 140 characters. Load Settings; if the canteen is closed, return
    CANTEEN_CLOSED.

3. Count the user's active orders today. If the count is at or above maxActiveOrders,
    return TOO_MANY_ACTIVE_ORDERS.

4. Inside prisma.$transaction(async (tx) => ...) :
     a. Load the requested items. If any is missing, archived or unavailable, throw
        ITEM_UNAVAILABLE.

                                                                   Page 17 of 33
Campus Canteen Live -- PRD

       b. For each item with limited stock, run tx.menuItem.updateMany({ where: { id,
          stock: { gte: qty } }, data: { stock: { decrement: qty } } }) . If the
          returned count is 0, throw OUT_OF_STOCK. This conditional update is what
          prevents overselling.

       c. Compute the total from database prices only. Prices sent by the client are ignored.
       d. Get the token with tx.dailyCounter.upsert({ where: { businessDate },

           create: { businessDate, lastToken: 101 }, update: { lastToken: {

          increment: 1 } } }) .
       e. Create the Order and its OrderItems.
   5. After the commit, call emitOrderCreated, emitDisplaySnapshot,
      emitMenuItemUpdated (for each item whose stock changed), emitQueueUpdates and
      scheduleStatsUpdate. Return HTTP 201 with the OrderDTO.

 6.2 Changing status (src/lib/orders/service.ts: transitionStatus)

   1. Load the order. Check the actor's role or ownership and the transition table in section
      3. Return FORBIDDEN or INVALID_TRANSITION if either check fails.

   2. Inside a transaction, run updateMany({ where: { id, version: expectedVersion,

       status: currentStatus }, data: { status: to, version: { increment: 1 },

      <timestamp>: now } }) . If the count is 0, return VERSION_CONFLICT with the
      current OrderDTO.
   3. For CANCELLED or REJECTED, increment stock back for every limited item in the
      order, in the same transaction.
   4. After the commit, call emitOrderUpdated, emitDisplaySnapshot, emitQueueUpdates,
      emitMenuItemUpdated (if stock was restored) and scheduleStatsUpdate.

 6.3 Queue position and wait estimate

      The queue is today's PLACED and PREPARING orders, sorted by createdAt.
      position = index in the queue + 1.
      etaMinutes = position × Settings.minutesPerOrder.
      Recompute after every change to the queue, and send queue:update to each student
      who has an order in it.

Architecture principles

1. The server is the single source of truth. Clients only render server state, apart from
    short-lived optimistic updates on the kitchen board.

2. HTTP for commands, WebSocket for events. Every write is validated, authorized and
    transactional, and the fan-out happens only after commit.

3. Snapshot plus events. Each page loads a snapshot over REST, patches it with events,
    and refetches the snapshot whenever the socket reconnects.

4. One process. Running more than one server instance would need the Socket.IO Redis
    adapter, which is out of scope.

8.2 Performance

    On a local network, 95% of events reach clients within 1 second of the write.
    The app handles 200 concurrent sockets on a normal laptop.
    The student menu is usable within 2 seconds on a mid-range phone over 4G.
    stats:update is throttled to once per second, and stock inputs are debounced by 500
    ms.

8.3 Resilience

    Socket.IO reconnects automatically with its default backoff. The header badge shows
    Live, Reconnecting or Offline.
    Every reconnect triggers a snapshot refetch (section 5.5), so updates missed while
    offline still appear.

Campus Canteen Live -- PRD

      After a server restart, all clients reconnect and resync without any manual refresh.
      On SIGINT or SIGTERM, the server closes Socket.IO and the HTTP server, then
      disconnects Prisma.
      Every route handler catches errors and returns the standard error shape. Stack traces
      are never sent to clients.

 8.4 Security and privacy

      The session JWT (7-day expiry, claims sub , role and name ) lives in an httpOnly,
      SameSite=Lax cookie, marked Secure in production. JWT_SECRET must be at least 32
      characters, and the server refuses to start without it.
      Passwords are hashed with bcryptjs (cost 10). Login errors never reveal whether an
      email exists.
      Every route handler and server layout checks the role through requireUser() or
       requireRole(...roles) . Role checks live in server components and route handlers,
      not in Next.js middleware.
      Mutating endpoints accept only application/json , which, together with SameSite
      cookies, blocks cross-site form posts.
      In-memory rate limits: POST /api/orders allows 5 per minute per user, and login allows
      10 per minute per IP. Excess requests return RATE_LIMITED.
      The ?next= redirect accepts only relative paths.
      The display gets token numbers only, and the kitchen gets first names only.

 8.5 Accessibility and compatibility

      WCAG 2.1 AA contrast, a keyboard-operable kitchen board and visible focus rings.
      Status is never shown by colour alone: every state has text or an icon. Status changes
      are announced with aria-live.
       prefers-reduced-motion turns off pulses and slide animations.
      Supports the latest Chrome, Edge, Firefox and Safari, Chrome on Android and Safari on
      iOS.
      Runs on Node.js 20 or later, on Windows, macOS and Linux.
      Times are shown in the canteen timezone (default Asia/Kolkata), and prices are shown
      as  with the Indian number format.

 11.1 Real-time behaviour

      A placed order appears on every open kitchen board within 1 second, with a flash and a
      tone, and no refresh.
      Start, Ready and Collected update the student's tracker and the counter display within
      1 second.
      A token that becomes ready pulses and chimes on the display, and it disappears when
      collected.
      Switching an item off, or its stock reaching 0, greys it out on every open menu within 1
      second. Carts containing it show a warning.
      Price and name edits appear live on open menus and in cart totals.

      The admin dashboard stats, chart and presence counts update live, no more than once

 11.2 Concurrency and correctness

      Two students ordering the last Samosa at the same moment: exactly one succeeds, the

      Stopping the server shows Reconnecting on every client. After a restart, every client
      resyncs without a refresh, including changes made while it was offline.
      Refreshing any page shows the same state as before the refresh.
      An old order:updated event (lower version) never overwrites newer state.

 11.4 Security and privacy

      Students cannot open /kitchen or /admin. The matching APIs return 403, and a
      student's socket never receives kitchen or admin events.
      A student cannot view or cancel another student's order.
      The display and its socket payloads contain no names or items.
      Rate limits return RATE_LIMITED.
